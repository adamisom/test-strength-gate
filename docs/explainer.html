test-strength-gate, explained

A guide to reading the code, written 9/25/26 against main at 75f4da1 (20 commits, 110 tests passing) and updated 9/28/26. Claude sub-agents built the code on 9/25/26, and three rounds of review by OpenAI's Codex hardened it. Where the design doc and the code disagreed, the code won, and the section near the end lists each disagreement and its correction.

test-strength-gate is a GitHub Action for Python projects that use pytest. For each test a pull request adds or changes, it runs the test against the code from before the pull request and reports whether the test would have noticed if the pull request's source change were missing.

The problem

A passing test run shows that the tests pass with the change in place, but it doesn't show that any of the new tests would fail without the change. A test that asserts almost nothing, or that checks behavior which was already true before the pull request, passes in exactly the same way as a test that pins down the fix. When coding agents write both the fix and its tests, and nobody reads them closely, the green check is often the only evidence a reviewer has.

The gate answers one narrow question per test. It takes the code from before the pull request, adds only the pull request's test-side changes, and runs the new and changed tests there. A test that fails there depends on the change. A test that passes there would have passed anyway. The hard part is that many tests fail on old code for a reason that says nothing about behavior, most often because they import a function that doesn't exist yet, so the gate has to tell those failures apart from failures of a check.

Each judged test gets one of five labels.

  • STRONG means the test fails at base for a behavioral reason, such as an assertion, a pytest.raises block that didn't raise, or another exception from the old code.
  • WEAK means the test passes at base. The label is a prompt for a reviewer and is expected for refactors.
  • INCONCLUSIVE means the test fails at base only because the API or input it uses is new, or because the run couldn't judge it.
  • BROKEN_AT_HEAD means the test doesn't pass on the pull request's own code, so nothing else about it can be judged.
  • SKIPPED means pytest skipped the test at base or at head.

The idea is not new. SWE-bench grades fixes the same way, with tests that must fail before the reference fix and pass after it. Adam built a version of this check at a previous job. The contribution here is a reusable Action and careful handling of the cases that fool a simple version.

The whole system on one page

The CLI entry point is cli.main, and the orchestration is one function, gate.run_gate. Everything else is a helper that one step of run_gate calls.

The code is small. Outside the plugin it is 877 lines of standard-library Python across nine modules (738 lines without blank lines), and the recorder plugin is another 285 lines that import only the standard library and pytest.

One pull request, end to end: cachier #279

cachier is a Python caching library. Pull request #279, written by GitHub Copilot, fixes a bug where enable_caching() had no effect on functions decorated while caching was off. The fix is a five-line change in src/cachier/core.py, and the pull request adds one test file with three tests. All three are named after the regression, and only one of them exercises it. The steps below follow a fresh run on 9/25/26 on 75f4da1, with base bd455da (the merge commit's parent) and head 6f2127f (the squash-merge commit). The run took about 1.5 seconds.

Why two tests named after the regression pass at base

At base, set_global_params builds a new settings object with dataclasses.replace and swaps it in, while enable_caching() and disable_caching() change the current object in place. A function decorated at base keeps the object that existed when it was decorated. So the bug only appears when set_global_params runs after decoration and caching is then turned on.

  • test_enable_caching_after_decorator_definition calls set_global_params(caching_enabled=False) before it decorates the function. After that it only calls enable_caching(), which changes the same object the function already holds, so it passes at base.
  • test_disable_caching_after_decorator_definition never calls set_global_params at all. enable_caching() and disable_caching() both worked before the fix.
  • test_original_issue_scenario decorates a method at class definition, then calls set_global_params(stale_after=...) and enable_caching() inside __init__. At base the method still holds the old object with caching off, so the second call runs the function again and the counter is 2 instead of 1.

The gate can't say why a weak test is weak. It only says the test would pass without the change, and a person then reads the test next to the diff, as above.

The verdict rules in classify.py

verdict(base, head) checks the head result first, because a test that doesn't pass on the pull request's own code tells you nothing about the old code. The order of the checks is the whole policy.

  1. If the test was skipped at head, it is SKIPPED.
  2. If the whole pytest run at head failed, such as a timeout or a conftest.py that won't load, it is INCONCLUSIVE, because the test's own result at head is unknown.
  3. If the test didn't pass at head for any other reason, it is BROKEN_AT_HEAD, whatever happened at base.
  4. If it passed at base, it is WEAK.
  5. If it was skipped at base, it is SKIPPED.
  6. If it wasn't collected at base, or it failed in setup, teardown, collection, or a failed run at base, or the base run loaded project code from outside the worktree, it is INCONCLUSIVE. A failing fixture at base is inconclusive even when its exception looks behavioral.
  7. Otherwise the test failed in its call phase at base, and failure_kind decides from the exception.
def failure_kind(exc_type, message, attr_owner=None, file_at_head=False, origin=""):
    if exc_type in ("AssertionError", "Failed"):
        return "assertion"
    if exc_type in MISSING_API_ERRORS:          # ImportError, ModuleNotFoundError, NameError
        return "missing_api"
    if exc_type == "FileNotFoundError" and file_at_head:
        return "missing_file"
    if exc_type == "AttributeError":
        return "other_error" if attr_owner == "builtin" else "missing_api"
    if exc_type == "TypeError" and ARGUMENT_MISMATCH.search(message or ""):
        return "unclear_call" if origin == "project" else "missing_api"
    return "other_error"

src/test_strength_gate/classify.py, with the docstring and comments removed. assertion and other_error become STRONG, and the other three become INCONCLUSIVE.

Each rule exists because a simpler rule gave a wrong answer.

  • Failed counts as a check. A pytest.raises block that doesn't raise fails with pytest's Failed: DID NOT RAISE, and Failed is not a subclass of AssertionError. The original brief counted only AssertionError as strong, which would have missed a common kind of strong test. Four of the evaluation's strong verdicts come from this rule, all in OpenEnv.
  • Import and name errors are inconclusive. A test that imports a function the pull request adds fails at base with ImportError before it checks anything. Calling that strong would be the most common false positive, and the design's second goal is to never make it. The demo in examples/demo.py shows it with test_word_count.
  • AttributeError depends on what lacked the attribute. The brief called every AttributeError inconclusive. But calc.new_func() failing on a module means a missing API, while find_word(...).upper() failing on None means the old code returned the wrong thing. Since Python 3.10 an AttributeError carries .obj, so the plugin records the kind of object. Only a builtin owner, such as None, a list or a string, makes the failure behavioral. A module, a class, any other object, or an unknown owner counts as a missing API. OpenEnv's 'list' object has no attribute 'get' is strong for this reason.
  • A FileNotFoundError for a file that exists at head is inconclusive. The input differs between the runs, not the code. A file that head doesn't have either stays strong, because then the old code failed to create something, which is behavior. The gate checks existence with git cat-file -e, which reads no contents and so works for binary files.
  • An argument TypeError is inconclusive, and where it was raised changes the reason. "unexpected keyword argument" usually means the test passes a new parameter. Python raises that error in the frame that made the call, so when the frame is in the project's own code, the old code may simply call something wrongly, which would be a behavioral failure. It still can't be strong, because a project decorator's *args, **kwargs wrapper raises the same error inside project code when a test passes a new keyword. The reason says the cause is unclear and names the line.
  • Any other exception is strong, with a conditional reason. A ValueError or KeyError from the old code means the test saw the old code behave differently, and the test passes at head. The rule is a heuristic, because something other than the source can differ between the runs. So the reason says where the exception was raised and ends with "Not a check, so inspect the cause: this is strong only if the old code caused it."

The stricter alternatives were measured on the evaluation. Five of the 20 strong verdicts come from exceptions other than a check, and the hand check found all five correct. Making every other exception inconclusive would have lost all five. Requiring old project code on the stack would have lost OpenEnv's two JSONDecodeErrors, which the test's own json.loads raises on a file the old code wrote.

A bare assert in a helper that pytest doesn't rewrite fails with an empty message, and the report used to say only "AssertionError". The verdict stays strong, but the reason now adds the failing line and a line from stderr. On robocop #1764 the reason reads "Fails at base on a check that has no message, at tests/formatter/__init__.py:106: assert exc_info.value.exit_code == exit_code. Last error on stderr: InvalidParameterError: ...", which shows that base rejected the new option.

The recorder plugin

plugin/tsg_recorder.py is a plain module that pytest loads with -p tsg_recorder, found because the runner puts its folder first on PYTHONPATH. It runs inside the project's own Python, so it works even when the gate runs from a different virtualenv, and it imports only the standard library and pytest. It reads its settings from environment variables (TSG_OUT, TSG_ROOT, TSG_SELECT, TSG_ORIGINAL_REPO) and writes one JSON file at the end of the session.

Selecting tests inside pytest, not on the command line

The brief said to pass the judged test IDs to pytest. But if one of those IDs doesn't exist, pytest prints "no tests ran" and exits with code 4 without running the IDs that do exist, as a check with pytest 9.1.1 on 9/25/26 confirmed. A test that is new at head can have an ID that base can't collect, so one such test would wipe out the whole base run. The runner therefore passes whole files, and the plugin drops every test whose ID isn't on the list.

def pytest_collection_modifyitems(config, items):
    select_file = os.environ.get("TSG_SELECT")
    if not select_file:
        return
    wanted = set(json.loads(Path(select_file).read_text()))
    keep, drop = [], []
    for item in items:
        (keep if _canonical_id(item.path, item.nodeid) in wanted else drop).append(item)
    if drop:
        config.hook.pytest_deselected(items=drop)
        items[:] = keep

IDs are rebuilt relative to the worktree root by _canonical_id, because pytest's own node IDs are relative to its rootdir, which depends on ini files and arguments and can differ between the two runs. The runner also passes --continue-on-collection-errors, because otherwise one file that fails to import stops the whole session.

Recording each phase

@pytest.hookimpl(hookwrapper=True)

    outcome = yield
    report = outcome.get_result()
    exc = call.excinfo

        "id": _canonical_id(item.path, item.nodeid),

        "message": str(exc.value)[:500] if exc else None,

        "missing_path": _missing_path(exc.value) if exc else None,
        ...

The live exception object exists only in pytest_runtest_makereport, on the process that ran the test. The plugin wraps that hook, reads the exception, and attaches plain strings to the report's user_properties, which pytest-xdist sends to its main process. pytest_runtest_logreport then stores one record per phase (setup, call, teardown). pytest-xdist itself is untested. pytest_collectreport stores the last E line of any file that fails to import, and pytest_sessionfinish writes the JSON.

For each failure the plugin records these fields.

  • exc_type and the message, cut to 500 characters.
  • attr_owner for an AttributeError, which is module, class, builtin or object, read from .obj. It is unset when code raises the error itself, as monkeypatch and mock.patch do.
  • missing_path for a FileNotFoundError inside the worktree.
  • raised_at, the innermost traceback frame, and local_at, the innermost frame inside the worktree. The gate's _set_origin turns these into test, project or library.
  • For an AssertionError with no message only, source_line and stderr_hint, each cut to 200 characters. The hint is the last captured stderr line that contains "error", "exception" or "traceback", or else the last line.

A small recorder beat two alternatives. JUnit XML writes the same <failure> element for an AssertionError and an AttributeError, as a check on 9/25/26 confirmed, and it can't carry the .obj that the attribute rule needs. A third-party JSON plugin would add a dependency to the project under test.

Keeping the base run honest

The base run must test base source with the pull request's test side, and nothing else. Every way it can drift produces a wrong verdict with no visible error, so most of the gate's code is about this.

Worktrees, not a checkout

The gate creates two detached git worktrees in a temporary folder and removes them in a finally block. It never touches the caller's checkout, which may have uncommitted changes, and which later CI steps expect to find unchanged. Stashing and checking out base was the alternative. A worktree for head as well means both runs happen under the same conditions, with the same paths and no local edits.

What the base worktree holds

  • Base source. Every file outside the test patterns stays at its base version, including the Python source under test.
  • The head test side. Every file that matches the patterns and that the pull request adds or changes is checked out at head, including conftest.py and non-Python fixtures. Only .py files other than conftest.py are passed to pytest, because on robocop a .robot fixture passed to pytest made it exit with code 4 and judge nothing.
  • Deletions. Test-side files the pull request deletes are removed with git rm before the copy. Removing first lets a file be replaced by a folder of the same name, which the first version of the fix crashed on.
  • Generated files. Git-ignored .py files in the caller's checkout are copied into both worktrees where their folder exists. On plumbum, hatch-vcs writes version.py at install time, a fresh worktree lacked it, and nothing was judged.
gitutil.remove_files(base_wt, deleted_test_files)
gitutil.checkout_files(base_wt, head_sha, result.test_files)
files = sorted({test_id.split("::")[0] for test_id in judged})
base_run = run(base_wt, files, select=list(judged))

PYTHONPATH, and catching a misrouted install

Projects usually install themselves, often with pip install -e .. An editable install points at the caller's checkout, which is at head, and a regular install puts a copy of head in site-packages. Either way the base run could import head code, every test would pass, and every test would look weak with no sign of the problem.

The path covers the two usual layouts, and a check catches the rest. At the end of each run, _misrouted_imports lists every loaded module that came from outside the worktree and is either a project module or was loaded from the caller's checkout outside its virtualenv. A project module is one whose top-level name the worktree defines, which means a .py file or package at the root or in src/, or any top-level package elsewhere, such as lib/mypkg. The walk skips hidden folders and folders such as tests, docs, vendor and build. If the base run has any misrouted module, every base result becomes INCONCLUSIVE and the reason names the module and its path. At head a misrouted module only adds a warning.

The check finds project packages by folder name, not from packaging metadata. It can therefore flag an unrelated dependency that happens to share a name with a folder in the checkout, which gives an inconclusive result rather than a false weak one. A namespace package (one without __init__.py) outside the root and src/ is not recognized. In the evaluation the check never fired, across nine repositories with editable installs.

Deleted and missing files, and other inputs

  • A data file the pull request adds under the patterns travels to base. The default pattern became tests/** after the first Codex review, instead of tests/**/*.py, for this reason.
  • A file that exists at head but is missing in the base run gives INCONCLUSIVE, with a reason that names the file and suggests a --test-glob.
  • A test-side file the pull request deletes is removed at base. Before 75f4da1, a test that checked a fixture was gone failed at base on the stale file and came out strong.
  • A non-Python file outside the patterns that the pull request changes or deletes (docs left out) stays at its base version, because the gate can't know it is test data. When some verdict is strong, the report names each such file at the top and marks deleted ones "(deleted)". The verdict itself doesn't change, and test_deleted_file_outside_the_patterns_is_named_at_the_top_of_the_report pins that it stays strong.

Choosing tests with syntax trees

A test counts as added when its ID exists at head and not at base. A test that exists at both counts as modified when its fingerprint changed. The fingerprint is ast.dump of the function's syntax tree, which includes decorators and leaves out comments, blank lines and line numbers.

def function_fingerprint(source, parts):
    ...
    node, context = None, []
    for name in parts:
        node = next((n for n in body if isinstance(n, (ast.ClassDef, *_FUNCTIONS)) and n.name == name), None)
        if node is None:
            return None
        if isinstance(node, ast.ClassDef):
            context.append(_class_context(node))
        body = node.body
    if body and _is_docstring(body[0]):
        node.body = body[1:]
    return "\n".join([*context, ast.dump(node)])

selection.py. parts is the path inside the file, e.g. ["TestThing", "test_b"], with any parametrize suffix removed.

  • Why syntax trees. Comparing collected test IDs misses an edited test, because it keeps its ID. Mapping diff hunks to line ranges flags a whitespace edit. A syntax tree ignores formatting and sees every change in logic.
  • Docstrings don't count. On instructor #1857, a test whose only change was its docstring came out as a false weak, so the docstring is dropped.
  • Class context counts. After the first Codex review, a test method's fingerprint also includes its class's decorators, bases and keywords, class-level statements such as pytestmark, setup and teardown methods, and autouse fixtures. It leaves out the other tests, plain helper methods, nested classes and the class docstring, so adding one test and one helper to a class doesn't re-judge all its old tests. Only a literal autouse=True is recognized.
  • A known surprise. Adding one case to a @pytest.mark.parametrize list changes the decorator, so every old case of that test counts as modified and usually comes out weak. The behavior is kept and pinned by test_f_new_parametrize_case_marks_old_cases_modified, because comparing each case's values is much more work.
  • Test file patterns. _glob_to_regex is a small matcher instead of fnmatch, whose * also matches /, and instead of PurePath.full_match, which needs Python 3.13. As in .gitignore, a pattern without a slash matches the file name in any folder.
  • Renames. --no-renames turns a rename into a delete plus an add, so a renamed test file's tests count as new.

The Action's base and head

On the pull_request event, actions/checkout checks out a merge commit that GitHub builds from the pull request's head and the current base branch. When the inputs are empty, the Action uses that merge commit's first parent as base and the merge commit itself as head.

if ! git rev-parse --verify --quiet 'HEAD^2' >/dev/null; then
  echo "::error::HEAD is not a merge commit. ..."
  exit 1
fi
if [ -n "$PR_HEAD_SHA" ] && [ "$(git rev-parse 'HEAD^2')" != "$PR_HEAD_SHA" ]; then
  echo "::warning::The merge commit's second parent is not the PR head commit, ..."
fi
BASE_SHA="${BASE_SHA:-$(git rev-parse 'HEAD^1')}"
HEAD_SHA="${HEAD_SHA:-$(git rev-parse HEAD)}"

action.yml, the "Run test-strength-gate" step.

  • Why not pull_request.base.sha. The first plan used it. It is the base branch tip when the event fired, which may not be the commit the merge was built on. The diff from HEAD^1 to HEAD is exactly the pull request's change on top of the base the merge used. DECISIONS.md entry 5 cites another project that counted tests from main as a pull request's own because of this.
  • Why not HEAD^2 as head. HEAD^2 is the pull request's own head. A diff from HEAD^1 to it would include main's newer changes, reversed. The merge commit is the code that would actually land.
  • Why fetch-depth: 2 is enough. HEAD^1 is an ancestor of HEAD, so the gate's merge-base step returns HEAD^1 without any more history. A test clones a merge commit with --depth 2 to pin this.
  • Why the gate still computes a merge-base. For callers who pass their own base, such as a base branch tip, diffing against the tip would pull in changes that landed on the base branch after the branch point.

The Action is a composite action, so it runs in the caller's job with the Python and packages the caller already installed. It refuses to run under pull_request_target, which carries the base repository's secrets and a write token while running the pull request's code. Every input reaches the shell script through an environment variable, never by pasting ${{ inputs.* }} into the script, so a crafted input can't inject shell commands. It needs no token and no write permission, which is all a pull request from a fork gets. The report goes to the job summary and to warning annotations. It is advisory by default, and --fail-on weak fails the step only when a test is weak and the pull request changes some Python source outside its tests.

The evaluation

An agent searched GitHub for merged pull requests written by coding agents that touch Python source and a test file, add at least one test function, and change fewer than 500 lines. The gate ran on 8 of them, plus robocop #1764 as an extra case for non-Python fixtures. Each repository got its own virtualenv with an editable install. Base was the merge commit's first parent and head was the merge commit, and the gate ran with a clean environment. All nine were rerun on 75f4da1 on 9/25/26 for this page, and every verdict, reason and test ID matched the saved reports in eval-reports/after-codex-round-2/. The 3 weak tests that never reach the changed code

Every weak verdict was checked by hand, by reading the test next to the pull request's diff.

  • cachier #279, two tests. Both are named after the regression, and neither runs set_global_params after decoration, as the walkthrough above shows against the base code.
  • instructor #1857, test_json_decode_error_caught_by_retry. The pull request names this test as its regression test. The fix stops _validate_model_from_json from wrapping json.JSONDecodeError in a ValueError. According to the hand check, the test's scenario raises a Pydantic ValidationError at base before it reaches that line, and the test accepts either type with assert isinstance(attempt.exception, (json.JSONDecodeError, ValidationError)), so it passes with or without the fix.

The other 4 weak tests are weak for an expected reason. One is a control for retry behavior that existed before (instructor), one checks an invariant the pull request didn't change (semantic-chunkers), and two constrain how the new code is written rather than what it fixes (OpenEnv). robocop's three weak tests check that bad values for a new option are rejected, and base rejects the whole unknown option, so they pass there.

All 3 inconclusive verdicts (verifiers #836) are correct, because each test calls EvalDisplay._display_max_concurrent, a helper the pull request adds. They also show a limit of the method. The pull request changes the display code to call that helper, no test checks the display, and the report can't say so.

What the evaluation measures, and what it doesn't

  • It measures whether each new test fails without the source change, on 30 tests from 8 pull requests, and a person agreed with every weak and inconclusive verdict.
  • It does not give a rate for agent pull requests in general. The sample is small and was chosen by a search with fixed filters.
  • It does not show that a strong test checks the right behavior, or checks it thoroughly. Strong only means the test depends on the change.
  • The strong verdicts were checked by their failure reasons, not by rereading every test. Four robocop strong verdicts were right for a partly wrong reason, because base rejected the new option before any behavior was checked.
  • It does not measure false strong verdicts from changed inputs, because no evaluation pull request changes or deletes a non-Python file outside the patterns, other than docs. The changed-inputs note never appeared.
  • It does not measure flakiness. Each test ran once per run, although every rerun gave the same verdicts.
  • It ran through the CLI with HEAD^1 and HEAD, not through the Action in a GitHub workflow.

What it does not do, and open issues

Out of scope for v0

  • It supports only Python and pytest, on Linux and macOS runners.
  • It doesn't judge whether a strong test checks the right behavior or checks it thoroughly.
  • It is not mutation testing. It makes exactly one change, putting back the old source, instead of hundreds of generated ones.
  • It doesn't post pull request comments, retry flaky tests, or block by default.
  • It doesn't judge a test whose only change is in a fixture it uses, unless that fixture is an autouse fixture or setup method in the test's own class.
  • --fail-on weak fails only on weak tests. Broken and inconclusive tests never fail the step.

Open issues

  • Strong from another exception is a heuristic. A data file the pull request changes outside the patterns stays at its old version at base, and a test can fail there with a KeyError unrelated to the source change and come out strong. The same can happen with a plain assertion. The report names such files, but a reader who skips the reason can overrate the verdict.
  • An argument TypeError inside the old code stays inconclusive, although it may have caught a behavioral bug.
  • A test of a new helper can't show the helper is used, as in verifiers #836. The README lists it as a limit.
  • The Action has never run in a GitHub workflow. Its shell step runs in a local test against a --depth 2 clone of a merge commit, and examples/action-integration.yml has not run. The tool's own CI passed on GitHub for 75f4da1, on Linux and macOS with Python 3.10 and 3.13.
  • No review of the last fix. Codex has not checked 75f4da1.
  • Environment gaps. Compiled extensions aren't rebuilt at base. A pull request that adds a dependency means the base run uses head's installed packages. A namespace package outside the root and src/ is not recognized as project code.
  • Inputs the note leaves out. Docs (.md, .rst, and files under docs/ and .github/) are left out of the changed-inputs note, and a .py helper outside the patterns counts as source.
  • A conftest.py that fails to load at head gives inconclusive rows, although it is often a break in the pull request.
  • Fixed limits. Each pytest run has a 900-second limit set in code, and a gate makes up to four runs. pytest-xdist is untested. Flaky tests can land in any bucket.

Open design choices

The STRONG label for exceptions other than a check

The counts are for the 8 evaluation pull requests, computed from the recorded exception types. With robocop added, the strong counts are 24, 19 and 19, because robocop's four strong verdicts are all assertions.

The first real GitHub workflow run

Nothing in the repository should claim the Action works in GitHub until it has run there. A small demo repository is built for it, with one pull request whose tests give a strong, a weak and an inconclusive verdict when the gate runs from the command line. It has not yet run on GitHub, and the check after it runs is the job summary and the annotations. Moving examples/action-integration.yml into .github/workflows/ is a smaller step toward the same goal, but it can't cover a pull request from a fork.

Smaller calls

  • Whether to compare the called function's signature at base and head, so that an argument TypeError from the old code can become strong.
  • Whether to repair a misrouted install by putting a folder such as lib/ on PYTHONPATH, instead of marking the base run inconclusive.
  • Whether a conftest.py import error at head should be broken rather than inconclusive.
  • Whether the changed-inputs note should also name .py helpers in folders such as testing/.
  • Keeping tests/** as a default pattern (recommended), and the name.

Where the docs and the code disagreed

Writing this page found the five disagreements below, and commit 1a0b055 corrected README.md, DECISIONS.md, the gitutil.changed_files docstring and the design doc to match the code. The details stay here because they describe what the code does. Only the timing figures in the last item were left as they were. None of these changes a verdict in the evaluation.

  • AttributeError owners. The design doc says an attribute missing on "a module, class or project object" means a missing API. The code treats any object whose type isn't a builtin as a missing API, including a third-party library's object, and it also treats an AttributeError with no .obj information (raised by hand, or by monkeypatch) as a missing API.
  • Which files pytest runs. The design doc says the gate runs pytest on the changed test files. The collect-only runs do use every changed .py test file except conftest.py, but the judging runs use only the files that hold a judged test.
  • Where the exception was raised. The design doc's first goal says each row shows where the exception was raised. The markdown reason shows it only for a strong verdict from another exception, an unclear argument TypeError, and a bare assertion. The JSON report has it for every failure.
  • The stderr hint. The design doc says the hint is the last stderr line that names an error. The code falls back to the last stderr line when no line names an error, and the reason shows at most 120 characters of the hint and 80 of the source line, although the plugin keeps 200.
  • Deleted files. DECISIONS.md entry 3 and the docstring of gitutil.changed_files said deleted test files are ignored. Since 75f4da1, deleted test-side files are removed from the base run, and both now say so.
  • Timing. The design doc says each pull request took 1 to 16 seconds. The rerun on 9/25/26 took 1.2 to 17.9 seconds of wall time, including Python startup, and the test suite took 21.8 seconds rather than the doc's "about 25".

The order to read the code

Read the modules in this order, starting with the two that hold the judgment calls. Before reading, run .venv/bin/python examples/demo.py from the repository, which builds a toy repository and shows one strong, one weak and one inconclusive test.

  1. classify.py. The rules here are the tool's main judgment calls. Be able to say which exception gives which verdict, and why the head checks come first.
  2. plugin/tsg_recorder.py. The pytest hooks, the exception fields, the output capture for bare assertions, and the misroute check. The design doc calls it the most subtle runtime code.
  3. runner.py. The subprocess environment, the handoff of selected IDs, the timeout, and when a run counts as failed as a whole.
  4. selection.py. What counts as a changed test, and which class context is left out.
  5. gate.py. The order of the steps, what travels to base, and where the file rows come from.
  6. gitutil.py, report.py, cli.py and action.yml, which are short and mostly mechanical.

For each module, read the tests that pin it. tests/test_units.py covers the rules, tests/test_scenarios.py runs one scenario repository that produces every verdict, tests/test_cli.py has one end-to-end test per bug fix, and tests/test_action.py runs the Action's shell step.

Ten common questions

Click a question to see the answer.

1. Isn't this just mutation testing?

It is mutation testing with exactly one mutant, and that mutant is the reverse of the pull request's own source change. So it costs one extra test run instead of hundreds, and it answers a narrower question, which is whether this test depends on this change. A strong test can still miss many other bugs, so a team could use both.

2. Why not use coverage of the changed lines?

A test can run every changed line and assert nothing, and coverage can't see that. The gate asks whether the test's outcome changes when the change is missing, which is what a reviewer wants to know.

3. How does it avoid calling a test strong when it only imports a function that doesn't exist yet?

ImportError, ModuleNotFoundError and NameError are inconclusive. So is an AttributeError on a module, a class, or any non-builtin object, which the plugin reads from the exception's .obj. An argument TypeError, such as "unexpected keyword argument", is inconclusive too. A test must also pass at head, or it is broken at head.

4. Is "any other exception is strong" safe?

Not always. It is a heuristic that is right when the old code caused the exception. A data file the pull request changes outside the test patterns stays old at base and can make a test fail for an unrelated reason. On the evaluation, making every other exception inconclusive would have been wrong on all 5 such verdicts, so the rule stayed, the reason now says where the exception was raised and to inspect the cause, and the report names changed files outside the patterns. The label itself is an open call.

5. Why does the runner pass whole files to pytest instead of the judged test IDs?

If one ID on the command line doesn't exist, pytest exits with code 4 and runs nothing, so one test that is new at head would wipe out the base run. The runner passes files with --continue-on-collection-errors, and the plugin deselects every test not on the list in pytest_collection_modifyitems. A judged test missing at base becomes inconclusive with "Not collected at base".

6. How do you know the base run tested base code and not an installed copy of head?

The runner puts the worktree root and its src/ at the front of PYTHONPATH, ahead of site-packages and editable-install finders, and turns off .pyc writing. Then the plugin lists project modules that loaded from outside the worktree. If the base run has any, every base result is inconclusive and the reason names the module and path. After Codex round 1, any top-level package in the worktree, such as lib/mypkg, counts as project code.

7. Why does the Action use the merge commit's first parent as base and the merge commit as head?

The merge commit is exactly the code that would land, and the diff from its first parent is exactly the pull request's change on top of the base the merge used. pull_request.base.sha can be stale. Using HEAD^2 as head would put main's newer changes into the diff, reversed. Because HEAD^1 is an ancestor of HEAD, fetch-depth: 2 is enough for the merge-base step.

8. How does it decide a test was modified, and what is the parametrize surprise?

It compares ast.dump of the test function at base and head, which ignores comments, formatting and line numbers, with the docstring dropped. For a method, it adds the class's decorators, bases, class-level statements, setup and teardown methods, and autouse fixtures. Adding one case to a parametrize list changes the decorator, so every old case counts as modified and usually comes out weak.

9. What did the evaluation find, and what doesn't it show?

On 30 new tests from 8 merged agent-written pull requests, 7 passed without the source change, in 4 of the pull requests. A hand check found 3 of the 7 never reach the changed code, including instructor's named regression test, and two cachier tests named after the regression. It doesn't show a general rate, doesn't show that strong tests check the right behavior, and never exercised the changed-inputs case or a GitHub workflow run.

10. How did you check code that an AI wrote, and why is the gate advisory by default?

A second model, Codex, reviewed it in three rounds. It found six more bugs, including a false strong from a deleted fixture, each fix has a regression test, and a rerun of the evaluation after each round changed no verdict. One Codex proposal was rejected with the evaluation's numbers. The gate is advisory because refactors and tests of existing behavior are legitimately weak, and a gate that blocks correct work gets turned off, so it shows its evidence and lets a reviewer decide.
